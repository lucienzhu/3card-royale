# Policy plugins · Arena 1.1

## This branch: structured actions v2

New policies use `royale-policy-v2` / `actions-v2`: one complete semantic action with fixed card IDs, validated and executed once. JS code, complete-move scoring and autoregressive generation share that boundary. ONNX declares a separate feature profile: `scoring-v2` (state + complete candidates → move scores) or `structured-v2` (state + prefix → token scores). Model choices do not redefine the action protocol.

[Action contract and migration](../docs/ACTIONS.md) · [JS template](../policies/templates/structured-policy.mjs) · [Training and measurements](../training/structured/README.md). Legacy `royale-policy-v1` remains supported. Its reference weights and Elo are frozen. The versioned interfaces below keep old submissions reproducible.


[简体中文](README.zh-CN.md) · [Arena](../arena.html) · [Evaluation protocol](../arena/README.md)

Submit a **policy**, either pure JavaScript or an ONNX network. Both run in the
browser and in the same local evaluator. Training is optional. GitHub Pages serves
static files; inference runs on the visitor's device. Official reference Elo is computed and published by the release workflow after review and merge.

## One policy, one folder

```
policies/entries/your-policy-v1/
  manifest.json
  policy.mjs        # OR policy.onnx
  README.md         # method, authors, source, license and reproduction
  validation.json   # generated by arena:submit; CI independently replays it
```

Copy a current entry and give it a **new immutable ID**. Add its manifest to
`policies/registry.json`. Do not replace an existing policy's weights/code under
the same ID after it has been rated. The artifact is at most 5,000,000 bytes;
update `artifact.bytes` and `artifact.sha256` with `node arena/stamp.mjs <id>`.
New manifests declare `royale-policy-v2` and `actions-v2`; v1 manifests remain valid. All declare rules `1.0.0`, episode `game`, public
information and whether the policy remembers observations within one game.

The primary extension point is this folder. The old `sdk/policy.js`,
`sdk/easy-policy.js` and `models/nn-policy/` remain frozen compatibility sources
for existing users and historical experiments. Built-in plugins adapt those
sources; the NN entry contains the same hash-verified model blob. GameCore stays
independent of policy selection.

Each registry entry declares `"github": "your-handle"` (without `@` or a URL).
The leaderboard links `@your-handle` to your GitHub profile. Use the same handle
as the new manifest's `author`. Registry attribution is display metadata; existing
rated manifests and scores remain immutable. Credit collaborators in README.md.

## Pure JavaScript

A **single self-contained ES module** exports a factory:

```js
export function createPolicy({random, sdk}) {
  return {
    act(observation) {
      return observation.legal_actions[Math.floor(random() * observation.legal_actions.length)];
    }
  };
}
```

For v2, `act` returns a complete semantic action (or a Promise of one), validated
against this observation. For v1 only, it returns the action’s index in the current
`legal_actions` list. Do not mix the two return types.
The detached, frozen observation is the [public SDK observation](../docs/SDK.md#state-ownership--observations).
Own hand and both public wound racks are visible; rival hand, deck order, RNG and
deal seed are not. The host applies the chosen legal action and checks it again.
Use injected `random()` for reproducible randomness, never `Math.random`, clock,
network, storage, environment variables or external services. For small games the
factory is called anew at every game boundary: keep optional public-observation
memory inside that instance, not module globals. No remote imports or dependencies.
Injected `actions` and `scoring` provide canonical actions and optional whole-move features. `sdk`, `core`, `code`, `easy` expose the pinned shared rules/helpers, never
the host's live game. Start with `templates/structured-policy.mjs` and the manifest example in [ACTIONS](../docs/ACTIONS.md#plugin-manifest). The old `templates/policy.mjs` is v1.

### Python or another language

Keep original source and its license if useful. **Use Codex or Claude Code to port
the strategy to JavaScript before submission**, so the exact submitted policy can
also be played on the web. See [porting prompt and parity workflow](templates/PORTING.md).
This is a contributor workflow, not a server-side translation service. Verify the
port on saved public observations, including play, defense, swaps and declines;
matching syntax alone is not enough. A Python-only submission is not a playable
Arena entry. A trained network can instead be exported to ONNX.

## ONNX

Both ONNX profiles use `royale-policy-v2` / `actions-v2`, FP32 and `memory: "none"`.

**Whole-move scoring** declares `features: "scoring-v2"`: `state [B,336] + candidates [B,N,72] → logits [B,N]`. N is the number of complete legal moves, up to 512 in this profile; no padding is sent to inference. The host selects argmax (first row on ties), maps the row to a canonical semantic action and validates it. The 72-feature descriptor matches the legacy scorer; fixed card IDs in the returned action replace the old external candidate index. Use `sdk/scoring.js` or Python `scoring.encode` for matching training features.

**Autoregressive generation** declares `features: "structured-v2"`:

| Name | Type | Shape |
| --- | --- | --- |
| `state` | float32 | `[B, 336]` |
| `prefix` | float32 | `[B, 396]` |
| `logits` | float32 | `[B, 65]` |

The host decodes at most six steps with conditional masks, then submits the complete move. Use `memory: "none"`. See [the action contract](../docs/ACTIONS.md).

### Legacy ONNX v1

Existing models keep `gym-v1` with dynamic candidate count:

| Name | Type | Shape |
| --- | --- | --- |
| `state` | float32 | `[1, 336]` |
| `candidates` | float32 | `[1, N, 72]` |
| `logits` | float32 | `[1, N]` |

N is the number of legal actions (at most 512); padding is removed. The host rejects
non-finite outputs and chooses argmax, first index on ties. Use `memory: "none"`.
The released NN is a behavioral-cloning baseline, not a reward-trained RL agent.
[Features, training and ONNX export](../docs/MODEL.md).

## Local validation → PR → release → Elo

1. Add a new immutable policy ID, its folder and registry entry.
2. Run `npm run arena:validate`, then `npm run arena:submit -- --policy <id>`.
   Commit the generated `validation.json`: four balanced games against Code AI.
3. Submit the PR. CI replays the receipt and requires matching final game hashes.
   Missing/stale receipts, illegal actions and timeouts block rating.
4. PRs and ordinary main pushes only validate playability. A new policy remains
   **Unrated** until **Publish Arena** runs: publishing a GitHub Release or manually
   dispatching that workflow on main. It plays **60 rated games** per pending policy,
   commits the leaderboard and rebuilds GitHub Pages. Unchanged scores are reused.

[Reference Elo method and limits](../arena/README.md): at most 3 entrants per PR,
10 rated policies per publication run, 180 seconds of match-running time. Publication costs
64 games per pending entrant including a fresh validation, independent of the catalog size. Browser play never
changes ratings. Fixed references are labeled separately; all new scores are
provisional. Godlike is excluded. Policies without matching results show **Unrated**.

## Execution boundary

Only merged, reviewed registry entries load in the website; no arbitrary JS URL or
user upload is executed. Workers keep the UI responsive and can be terminated on
failure. **A Worker is not a security sandbox:** it can use network APIs; local Node
plugins could access the machine. Review first and evaluate unfamiliar PRs in a
credential-free, network-disabled container ([execution boundary](../arena/README.md#execution-and-publication-boundary)).
Do not run PR code in a privileged `pull_request_target` workflow.

Web inference uses single-thread ONNX Runtime Web / WASM in a Worker. Local rating
limits are 1 s per decision, 30 s to load and 4,096 host steps per small game.
The interactive browser allows 3 s per decision for slower phones, and visibly
falls back to Easy on failure. Official evaluation **does not fall back**: failures
abort the run without publishing partial ratings. See the protocol for latency and
rating limits.
