# Localization

The static GitHub Pages site supports `zh-CN`, `en`, `ja`, `ko` and `es`.

## Coverage

- Playtest: table, settings, practice, first-game hints, rules, replay, results and PNG share layouts.
- About, Identity, Arena, full rulebook, hand research and the live Design System.
- GitHub README and full rulebooks in all five languages.
- Japanese, Korean and Spanish technical guides covering SDK, actions, Gym, models, training, policy submissions and contribution checks.
- A one-page A4 rules PDF for each language.
- Language-aware navigation and document metadata.

Chinese retains 深圳花牌; other locales retain 3Card Royale and the official English alias Shenzhen Flower Cards. Card identities, policy identifiers, protocol tokens, code examples, GitHub handles and user-entered names are not translated. Detailed API references and experimental archives remain in their original language; the localized technical guides link to them explicitly.

The Learn and Rules pages download the matching language PDF. Documentation links open the native rulebook or the relevant technical-guide section. `SZI18n.onePagerPath` and `documentPath` centralize these routes.

## Sources and selection

`app/i18n.js` provides locale selection, the shared picker and `SZI18n.pair(zh, en, lang)` / `translate(english, lang)`. `app/locales/catalog.js` stores rows of English source, Japanese, Korean and Spanish. `app/locales/rules.js` contains all eight full rule chapters in the three added languages. Existing Chinese/English sources remain in their page or component.

Selection precedence is URL `?lang=…`, saved `gk_ui_language`, browser language, then English. Regional forms such as `ja-JP`, `ko-KR` and `es-MX` normalize to supported locales. Changing the picker updates the URL and saved preference without resetting the game.

Production components should use `SZI18n.pair` directly. The shared DOM adapter translates static English page copy; existing playtest and probability adapters first resolve their Chinese/English source. Source text is retained so language switching is reversible. Code, preformatted data and `[data-no-i18n]` are excluded. Components that render localized text or opaque user names own those nodes.

## Repository documentation

- `README.{ja,ko,es}.md`: project overview and entry points.
- `docs/RULES.{ja,ko,es}.md`: full rulebooks generated from `app/locales/rules.js` by `python3 scripts/build-rule-docs.py`. Do not edit generated Markdown independently.
- `docs/GUIDE.{ja,ko,es}.md`: localized developer guides with stable `sdk`, `actions`, `gym`, `models`, `training`, `arena`, `contribute` and `validation` anchors. Keep code examples and measured values aligned with their referenced source documents.
- `scripts/onepager-locales.json`: A4 copy for the three added languages; layout and Chinese/English copy remain in `scripts/build-onepager.py`. See [PDF build and visual review](ONE_PAGER.md).

## Adding copy

1. Add one catalog row with complete sentences and identical `{placeholder}` names in each language.
2. Translate the template before substituting a player name; names may themselves equal a UI key such as `Attack`.
3. Keep small games distinct from the full race to Ace, and playable wound cards distinct from healing.
4. Keep concise labels in controls and complete accessible labels. Reuse the shared font and control tokens.
5. For rule changes, update all five full rulebooks and A4 references, regenerate the three Markdown rulebooks, and check rule facts against GameCore.
6. For SDK, protocol or training changes, update the three technical guides alongside their English/Chinese references. Keep historical experiment records unchanged.

## Verification

`npm test` includes `tests/i18n.cjs`: catalog uniqueness, nonempty translations, placeholder parity, locale precedence, complete rule chapters and localized SVG exports, language-specific documentation/PDF routes, relative documentation links. Run `python3 scripts/build-rule-docs.py --check` separately to verify generated rulebook parity. Browser QA additionally checks language cycling, tutorial completion, state preservation, narrow layouts and light/dark themes. Viewport emulation is not physical-device testing or native-speaker review.
